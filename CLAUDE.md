# Trip Canvas — Claude working rules

This is a demo Gen AI app.

## Start of every session
- Read the system design doc and the implementation plan in `/docs` before doing anything else:
  - `docs/Trip canvas — system design.md`
  - `docs/Trip canvas — implementation plan.md`

## Keeping the docs in sync
- If a decision made during the session contradicts the system design or the implementation plan, point out the contradiction, offer to update the relevant doc, and ask for permission.
- Update the docs only after explicit approval.
- `docs/` is gitignored: the docs live locally only and are never committed.

## Tests
- Never colocate tests with source files. Put unit tests in the package's `test/` folder, mirroring the `src/` structure: `apps/server/src/routes/chat.ts` → `apps/server/test/routes/chat.test.ts`.

## UI components
- shadcn/ui components live in `apps/web/src/components/shadcn/`. They are added with the shadcn CLI (`pnpm dlx shadcn@<version> add <name>` from `apps/web`), never written by hand.
- AI Elements (chat components for the AI SDK) live in `apps/web/src/components/ai-elements/`, added the same way from `https://registry.ai-sdk.dev/<name>.json`. They import `cn` from `@/lib/utils`, so keep that re-export.
- Do not edit files in those folders unless the user explicitly asks to customise a component.
- Every new UI component, or new visible state of one, gets a Storybook story in `apps/web/stories/`, mirroring `src/`: `src/components/catalog/PlaceCard.tsx` → `stories/components/catalog/PlaceCard.stories.tsx`. A component added with the shadcn CLI gets its story through the component of ours that uses it. Stories mock data with MSW, never real APIs.

## Code style
- Name a component's props type `<ComponentName>Props` (e.g. `ComposerProps`); no bare `Props` and no inline prop types.
- Exception: components in one file that take exactly the same props share one type, named after what they take (e.g. `MessagePartsProps` for `MessageActivity` and `MessageSources`). Give a component its own type again as soon as its props differ.
- Don't spread `...props`; destructure and pass each prop explicitly unless forwarding everything is genuinely needed.
- Generated component folders (see above) are exempt.

## React components
- No render functions (`renderPart(part)` and the like) that return JSX: make them components (`<MessagePart part={part} />`) with their own props type.

## Data loading
- Never load data in a `useEffect` and then put it into state with `setState`. Load async data (IndexedDB, HTTP, anything awaited) with TanStack Query (`useQuery`, `useMutation`) instead.
- Name hooks that wrap them after what they are: `use<Thing>Query` for `useQuery`, `use<Action>Mutation` for `useMutation` (e.g. `useSavedMessagesQuery`, `useSaveMessagesMutation`).
- Put each such hook in `apps/web/src/hooks/`, in a file named after the hook (`hooks/usePlaceDetailsQuery.ts`), together with the fetch function and types it needs. Its test goes to `apps/web/test/hooks/usePlaceDetailsQuery.test.ts`.

## Code review
- Skip generated code when reviewing a PR or a diff; do not comment on it or count it toward PR size:
  - `apps/web/src/components/shadcn/**` and `apps/web/src/components/ai-elements/**` — copied in by the shadcn CLI.
  - `pnpm-lock.yaml` — generated by pnpm.
  - `apps/web/.storybook/public/mockServiceWorker.js` — generated by `msw init`.
- Exception: flag it if a PR hand-edits a file in those component folders without saying why.
- These paths are marked `linguist-generated` in `.gitattributes`, so GitHub collapses them in PR diffs.

## PR size
- Keep each PR under 500 changed lines (generated code excluded, see above).
- A PR adds at most two outside data APIs (e.g. one new OpenTripMap client plus a Nominatim tool). Split anything bigger into stacked PRs.

## Git workflow
- Before starting any coding task, create a new branch off the current base with a clear, descriptive slug (e.g. `feat/hello-page-with-date`).
- Do not commit until the user has reviewed the changes and said to commit.
